# Overview

This exercise demonstrates the development, validation, and automated response of a custom Wazuh detection rule.

The exercise extends the Wazuh SOC home laboratory by creating a custom detection rule specifically for SSH authentication failures and binding that rule to the `firewall-drop` Active Response mechanism.

The objective was to demonstrate that a SOC analyst can move beyond relying exclusively on built-in Wazuh detection rules and develop a custom detection-and-response workflow based on the specific requirements of a monitored environment.

The exercise demonstrated how Wazuh can:

- Detect a specific SSH authentication failure condition.
- Assign a custom rule ID.
- Assign an appropriate alert severity.
- Associate the detection with MITRE ATT&CK.
- Generate a custom security alert.
- Bind the custom rule to an Active Response.
- Automatically invoke `firewall-drop`.
- Record the Active Response execution.
- Add a firewall block for the detected source IP.
- Remove the firewall block after the configured timeout.
- Provide centralized evidence for investigation and validation.

The exercise was performed within the isolated Wazuh SOC home laboratory environment.

The detection-engineering workflow demonstrated was:

Define → Configure → Validate → Detect → Respond → Verify → Document

# Custom Detection Rule

A custom Wazuh detection rule was created with the rule ID:

`100002`

The rule was designed to identify SSH authentication failure activity originating from the monitored laboratory source.

The custom detection generated the following alert description:

```text
Custom detection: SSH authentication failure from monitored lab source 172.20.10.4.
```

The custom rule was configured with:

Rule ID: 100002
Rule Level: 8

The rule was also associated with the following MITRE ATT&CK technique:

T1110.001 — Password Guessing

The rule was assigned the following groups:

local
syslog
sshd
authentication_failed
custom_detection
ssh

This allowed the event to be identified as a locally developed detection while retaining useful SSH and authentication classifications.

# Detection Logic

The custom rule was designed around the SSH authentication-failure event generated by the Ubuntu endpoint.

The monitored endpoint generated an SSH authentication failure containing information such as:

Failed password for root from 172.20.10.4

The important investigative fields included:

| Field       | Value                  |
| ----------- | ---------------------- |
| Source IP   | `172.20.10.4`          |
| Destination | `172.20.10.5`          |
| Username    | `root`                 |
| Service     | `sshd`                 |
| Event Type  | Authentication Failure |
| Custom Rule | `100002`               |
| Alert Level | `8`                    |

The custom rule therefore provided a controlled detection mechanism for the specific SSH authentication activity being simulated in the laboratory.

# Firewall-Drop Active Response Configuration

The existing Wazuh firewall-drop command was configured as an Active Response command.

The command configuration included:

<command>
  <name>firewall-drop</name>
  <executable>firewall-drop</executable>
  <timeout_allowed>yes</timeout_allowed>
</command>

This configuration makes the firewall-drop executable available to the Wazuh Active Response subsystem.

The custom rule was then bound to the Active Response using:

<active-response>
  <command>firewall-drop</command>
  <location>local</location>
  <rules_id>100002</rules_id>
  <timeout>300</timeout>
</active-response>

The important configuration parameters were:

| Parameter       | Value                    |
| --------------- | ------------------------ |
| Command         | `firewall-drop`          |
| Location        | `local`                  |
| Triggering Rule | `100002`                 |
| Timeout         | `300 seconds`            |
| Response Type   | Firewall source blocking |

The five-minute timeout was selected so that the laboratory could demonstrate both containment and automatic recovery.

# Lessons Learned
- Custom Wazuh rules allow organizations to create detections specific to their own environments.
- Rule severity should reflect the potential security significance of the detected activity.
- MITRE ATT&CK mappings provide useful context for custom detections.
- Configuration validation should be performed before restarting security infrastructure.
- A successful service restart confirms that the updated Wazuh configuration was accepted.
- Detection should always be tested using a controlled security event.
- Active Response configuration should be validated through actual execution rather than configuration inspection alone.
- Wazuh Active Response provides a mechanism for connecting detection logic to automated containment.
- The add operation provides evidence of the containment stage.
- The delete operation provides evidence of the recovery stage.
- Timeouts are important when implementing temporary automated containment.
- Centralized Wazuh logs provide useful evidence for validating detection and response workflows.
- Custom detection engineering is an important SOC skill because organizations often require detections that are not provided by default rules.
- Automated response should always be carefully scoped to avoid disrupting legitimate activity.
- Detection, response, validation, and documentation should be treated as one operational workflow.
